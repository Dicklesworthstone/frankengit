# FrankenGit reality check and bridge plan — 2026-10-30

FrankenGit has a substantial native Git node and increasingly useful forge paths. The implementation has advanced materially beyond the October 21 assessment. It still does not deliver the complete authenticated team forge, sponsored agent workflow, independently recovered deployment, scale envelope, or release promised by the plan. Its main problem is now completing and qualifying the joins between real components. Neither crate count nor closed-Bead count measures that distance.

**Source boundary:** full intake and clean-source JS execution at `bab013c14fe7973a3f0eed0a1abd10046c770061`; follow-on source review through `a28eddaba44d0903707570ad20f822c1b78265bf`. Shared `main` advanced during the audit. The seven intervening commits change 21 files; their implementation changes were inspected separately. JS test/profile directories are unchanged across those revisions, but the executed results below remain attributed to `bab013c1`. No native-test or whole-workspace result is transferred between revisions. This document is prepared on the isolated branch `codex/reality-check-20261030`; the audit makes no product-code changes.

**Consumer, gate, observed defect and retirement:** the owner and independent batch verifier use this existing bridge to choose the work gating usable team operation, agent operation, recovery and release. The observed defects are incomplete product composition, unverified acceptance, finite-history ceilings, and unresolved construction contracts. Supersede this document in place after the next revision-bound assessment. It grants no deployment authority, closure credit, architecture ruling or gate exemption.

## 1. Direct answers

1. **What is real?** Native SHA-1/SHA-256 objects, pack/delta/DEFLATE, import/export, quarantined receive, upload-pack, three Git carriers, embedded authority, sealed transactions, native PR/review/protection/merge paths, issue operations, indexed retrieval, trusted workflows, sparse host workspaces, backup components, verified reads and historical queries. These have substantial implementations and checked-in tests. The audit's fresh execution is narrower than that source inventory.
2. **What is incomplete?** A supported authenticated team deployment; full current protected-PR/CI acceptance; sustained history scaling; canonical agent execution through ECC; hostile-code isolation; composed GC/repair/RaptorQ/compaction; an off-node authority/fabric deployment; broader graph/ATP consumers; a qualified native release; and the hosted, enterprise, package and federation scope.
3. **What controls progress?** Independent verification and the executable build path, unresolved owner decisions, then completing the team-day, agent-day and destroy/restore outcomes. Verification debt is again at its configured hard limit. Adding feature slices without draining that debt increases the gap between source and accepted capability.
4. **Would finishing all open work finish the vision?** The remaining tracker now has owners for every major capability class in this checklist. That is a much better position than an untracked vision. It is still insufficient to infer completion: several older closed items were library slices, current acceptance is unexecuted or disputed, and contradictory scope/construction contracts remain. Completion requires the full original acceptance of the open work, the independent closure audit, resolved owner rulings, and the product/release exits at named revisions.
5. **Which goals have no Bead?** No wholly unowned major goal was established by this review. Unfinished code is not automatically `NO_BEAD`. Existing owners cover the observed defects, including remote fixture selection, live operator evidence, team/agent integration, recovery, security, economics and external adoption. No duplicate epic is warranted. This is a capability-class coverage finding, not a proof that every sentence in 393 Markdown documents has an exhaustive acceptance mapping.

## 3. What has improved since October 21

- **Agent context now has consumers.** The earlier “uncalled bridge” conclusion is obsolete. `context_packet_for_run` is used by native retrieval and the shared document adapter. `fg agent context`, authenticated HTTP `source/agent-context`, and independently granted MCP `frankengit_agent_context` reach that implementation. They bind an authenticated source position and preserve untrusted excerpts and omissions. They remain read-only invocation-local runs. Native run/effect journals and the concrete Beads task adapter also exist; journal creation/recovery does not constitute a resumed executing agent controller. See [agent context](AGENT_CONTEXT_COMMAND.md) and [the node journal](../crates/fgit-node/src/agent_journal.rs).
- **Receive publication really batches.** [The admission microbatch driver](../crates/fgit-admission/src/microbatch.rs) is called from production receive paths. Up to 64 independent decisions and 1 MiB of batch bytes share an exact-predecessor CAS, retaining each child seal/outcome and wire-order semantics. Non-atomic recovery admits up to 16,384 commands; atomic/import transactions retain 4,096. This corrects the old one-CAS-per-ref statement. Cross-session lane/combiner/witness integration and measured contention acceptance remain open.
- **The total-history merge cliff has been addressed in source.** [Merge preparation](../crates/fgit-forge/src/preparation.rs) uses exact frontier merge-base traversal; [native candidate admission](../crates/fgit-admission/src/merge/native/objects.rs) can validate additions above authenticated selected objects. It is obsolete to say every repository over 4,096 total commits or 100,000 total files must fail. `rffg` and `lh8z` retain historical large-repository observations and still need independent acceptance. Deep/wide ancestry, multiple bases, reviewed full-closure paths and independent tree/byte limits remain bounded. The new verified commit-metadata cache is a real consumer, not completion of all graph generations.
- **Repeated serving work has been reduced.** Authority closure prefix reuse, pack-computation caching, received-pack reuse, and visible upload projection reuse exist. At `a28eddab`, the previous projection's verified object facts seed a new walk while current selection and logical budgets are reapplied. Exact matching received packs can avoid recompression. These caches do not establish persistent checkpointing, whole-service RSS bounds or sustained scale. `1tl9` records a native pack-cache test expectation conflict observed at `60746dd1`/`81966cee`; this audit did not execute that native test at either assessed revision.
- **Private candidate custody reaches more paths.** Imports, bundles, reviewed workspaces and native merge candidates now retain synced private objects through preparation. Refused preparation need not place the whole candidate in the public object fabric. A later successful placement followed by CAS loss, process death or abandoned retained history still needs GC. This is a real mitigation, not `fg gc` or repair completion.
- **Scrub is a native read path.** At `a28eddab`, the object fabric verifies native identity, length and strong commitment through 64 KiB chunks. `fg scrub` checks page allowance before payload reading and permits explicit independent object/page/sweep budgets up to the documented limits. It does not repair, delete, prove graph closure or certify unobserved pages. See [native scrub](NATIVE_OBJECT_SCRUB.md).
- **Several old contract defects were repaired.** The verifier no longer exports the prohibited local-build bypass. Licence metadata and the production `#[expect]` checker hole were repaired earlier. The fsqlite family is now checksum-pinned at 0.4.10; the later `6097e50f` adds a missing node test dependency. These changes must not be reported as still absent, or promoted to an unexecuted current full gate.
