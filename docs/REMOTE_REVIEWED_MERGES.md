# Remote exact-candidate reviews and reviewed merges

The external operator PR client now supports `approve`, `request-changes`,
`withdraw`, and `merge` in addition to the original six form-only operations.
It calls the existing native Rust review/merge APIs. It does not compute a Git
merge, interpret a pack, validate ancestry, or turn a transport hash into approval.
Related beads: `frankengit-root-doctrine-x2mv.4.13` and `.4.20`; both remain partial.

## Select an exact existing candidate

Obtain the candidate bundle, merge base, candidate commit and subject from the
native candidate tooling. Inspect the candidate's actual changes before approving
it or selecting it for merge. This client does not produce candidates or perform
that review. The existing browser/native inspection workflow remains separate.

`preparePull(input, token, bundleBytes)` accepts the existing endpoint and scope
shape plus the PR number, action, and these exact fields:

- All four actions: `pull_request_version`, `policy_epoch`, `source_ref`,
  `target_ref`, `source_tip`, `target_tip`, `merge_base`, and `candidate_commit`.
- Review actions: `expected_version` of the authenticated reviewer's own stream
  and a nonblank `reason` (at most 4,096 UTF-8 bytes). A withdrawal needs an
  existing nonzero reviewer-stream version and takes no bundle.
- Merge: `required_reviewers` (1–32 distinct principal IDs, excluding the
  submitting principal) and `method`, explicitly `merge-commit` or `squash`.

Numbers, versions and policy epochs are canonical decimal strings. References
are exact UTF-8 branch names; native OIDs are raw lowercase hex in the selected
SHA-1 or SHA-256 domain. The source/target refs must differ. Neither reviewer
identity nor a policy override is accepted as a form field. An explicit required
reviewer set does not override stricter native branch protection.

Approval, request-changes and merge require a nonempty Node `Buffer`, at most
16 MiB, containing the original candidate bundle. Preparation binds its byte
length and SHA-256 transport checksum in a separate candidate-intent schema and
`fgpc1-` key domain. The original `fgp1-` intent schema and serialization are
unchanged. No bundle bytes or paths are embedded in the JSON intent. The caller
must retain the bundle separately and provide it for a new submission.

## Publish or recover

```js
const intent = preparePull(input, token, bundle);
// Save the intent and bundle before sending. Inspect the actual native candidate.
const result = await submitPull(intent, token, {
  confirmKey: intent.key,
  confirmCandidate: intent.fields.candidate_commit,
  ...(intent.action === 'merge' ? { confirmMergeMethod: intent.fields.method } : {}),
  ...(intent.action === 'withdraw' ? {} : { bundle }),
});
```

Candidate and merge-method confirmations are explicit user consent, not proof
of review, a runner attestation or authority. An approval is the authenticated
principal's statement. The server independently validates the bundle, subject,
reviewer stream, current source, policy and merge requirements at publication.
There is no fast-forward fallback, strategy substitution, implicit tip refresh,
new-key retry, or automatic approval. The original fast-forward operation still
requires its separate confirmation and does not acquire reviewed-merge semantics.

Submission uses one bounded operation deadline, the same authenticated outcome
preflight, one exact multipart upload (ordinary form for withdrawal), and a
matching outcome confirmation. All candidate coordinates, byte/text refs,
predecessor versions, policy epoch, reviewer requirements, selected method,
principal, repository incarnation and terminal decision are checked. A missing
or conflicting receipt leaves the outcome unknown. Valid publication evidence
is retained on errors during confirmation and suppresses resubmission.

`recoverPull(intent, originalOrRotatedToken)` needs no bundle and cannot upload
one. It only looks up the original principal's original key. A previously
observed terminal also suppresses upload when `submitPull` is invoked without a
bundle. The native forms still lack an atomic expected-incarnation precondition;
client preflight cannot create one. Do not repoint a live endpoint at a different
repository during a command.

## Executed validation

`node --test tests/operator/remote_pull.test.mjs tests/operator/remote_pull_review.test.mjs`
exercises the complete production modules with real HTTP/TLS sockets and explicit
native-schema peers, including opaque binary payloads, both hash domains,
full-width counters, method/reviewer mismatches, lost replies, credential rotation,
strict limits and cancellation. It does not execute Rust `fg`, native Git bundle
validation, admission, ancestry, or branch protection. TLS test certificates are
generated by a test-only OpenSSL invocation; no dependency is added to production.
