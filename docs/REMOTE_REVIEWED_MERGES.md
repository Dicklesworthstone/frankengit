# Remote exact-candidate reviews and reviewed merges

The external operator PR client now supports `approve`, `request-changes`,
`withdraw`, and `merge` in addition to the original six form-only operations.
It calls the existing native Rust review/merge APIs. It does not compute a Git
merge, interpret a pack, validate ancestry, or turn a transport hash into approval.
Related beads: `frankengit-root-doctrine-x2mv.4.13` and `.4.20`; both remain partial.

## Select an exact existing candidate

Obtain the candidate bundle, merge base, candidate commit and subject from the
native candidate tooling. Inspect the candidate's actual changes before approving
it or selecting it for merge. This client does not produce candidates or perform
that review. The existing browser/native inspection workflow remains separate.

`preparePull(input, token, bundleBytes)` accepts the existing endpoint and scope
shape plus the PR number, action, and these exact fields:

- All four actions: `pull_request_version`, `policy_epoch`, `source_ref`,
  `target_ref`, `source_tip`, `target_tip`, `merge_base`, and `candidate_commit`.
- Review actions: `expected_version` of the authenticated reviewer's own stream
  and a nonblank `reason` (at most 4,096 UTF-8 bytes). A withdrawal needs an
  existing nonzero reviewer-stream version and takes no bundle.
- Merge: `required_reviewers` (1–32 distinct principal IDs, excluding the
  submitting principal) and `method`, explicitly `merge-commit` or `squash`.

Numbers, versions and policy epochs are canonical decimal strings. References
are exact UTF-8 branch names; native OIDs are raw lowercase hex in the selected
SHA-1 or SHA-256 domain. The source/target refs must differ. Neither reviewer
identity nor a policy override is accepted as a form field. An explicit required
reviewer set does not override stricter native branch protection.

Approval, request-changes and merge require a nonempty Node `Buffer`, at most
16 MiB, containing the original candidate bundle. Preparation binds its byte
length and SHA-256 transport checksum in a separate candidate-intent schema and
`fgpc1-` key domain. The original `fgp1-` intent schema and serialization are
unchanged. No bundle bytes or paths are embedded in the JSON intent. The caller
must retain the bundle separately and provide it for a new submission.

## Publish or recover

```js
const intent = preparePull(input, token, bundle);
// Save the intent and bundle before sending. Inspect the actual native candidate.
const result = await submitPull(intent, token, {
  confirmKey: intent.key,
  confirmCandidate: intent.fields.candidate_commit,
  ...(intent.action === 'merge' ? { confirmMergeMethod: intent.fields.method } : {}),
  ...(intent.action === 'withdraw' ? {} : { bundle }),
});
```

Candidate and merge-method confirmations are explicit user consent, not proof
of review, a runner attestation or authority. An approval is the authenticated
principal's statement. The server independently validates the bundle, subject,
reviewer stream, current source, policy and merge requirements at publication.
There is no fast-forward fallback, strategy substitution, implicit tip refresh,
new-key retry, or automatic approval. The original fast-forward operation still
requires its separate confirmation and does not acquire reviewed-merge semantics.

Submission uses one bounded operation deadline, the same authenticated outcome
preflight, one exact multipart upload (ordinary form for withdrawal), and a
matching outcome confirmation. All candidate coordinates, byte/text refs,
predecessor versions, policy epoch, reviewer requirements, selected method,
principal, repository incarnation and terminal decision are checked. A missing
or conflicting receipt leaves the outcome unknown. Valid publication evidence
is retained on errors during confirmation and suppresses resubmission.

`recoverPull(intent, originalOrRotatedToken)` needs no bundle and cannot upload
one. It only looks up the original principal's original key. A previously
observed terminal also suppresses upload when `submitPull` is invoked without a
bundle. The native forms still lack an atomic expected-incarnation precondition;
client preflight cannot create one. Do not repoint a live endpoint at a different
repository during a command.

## Durable candidate CLI

The same `scripts/remote_pull.mjs` entry point now saves candidate bytes alongside
the exact request. Use private owner-controlled input, token and bundle files
outside a Git worktree, as required by the original remote PR operator profile.
No extra executable, package, native server route or authorization grant is added.

For illustration, an approval input has this shape. Replace every example
identity, version, policy epoch and native OID with independently selected values
from the existing native PR/candidate workflow; these example OIDs are not a
usable candidate. Review the actual candidate contents before preparing approval.

```json
{
  "endpoint": "https://forge.example/repo.git",
  "scope": {
    "tenant_id": "11111111111111111111111111111111",
    "repository_id": "22222222222222222222222222222222",
    "repository_incarnation": "33333333333333333333333333333333",
    "principal_id": "44444444444444444444444444444444",
    "object_format": "sha1"
  },
  "number": "37",
  "action": "approve",
  "fields": {
    "pull_request_version": "2",
    "policy_epoch": "3",
    "source_ref": "refs/heads/topic",
    "target_ref": "refs/heads/main",
    "source_tip": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "target_tip": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "merge_base": "cccccccccccccccccccccccccccccccccccccccc",
    "candidate_commit": "dddddddddddddddddddddddddddddddddddddddd",
    "expected_version": "0",
    "reason": "Reviewed the exact candidate changes."

```

```sh
node scripts/remote_pull.mjs prepare --input /private/approval.json \
  --token-file /private/reviewer-token --bundle /private/reviewed.bundle \
  --request-dir /private/approval-37
node scripts/remote_pull.mjs inspect --request-dir /private/approval-37
node scripts/remote_pull.mjs send --request-dir /private/approval-37 \
  --token-file /private/reviewer-token --confirm-key EXACT_SAVED_KEY \
  --confirm-candidate EXACT_CANDIDATE_OID --record /private/approval-result.json
```

`inspect` is offline saved-intent inspection. It is **not** a Git diff, live
policy check or independent proof that anyone reviewed the candidate. It prints
private command data but never prints the token or binary bundle contents.
For request-changes use that action with an explicit reviewer-stream predecessor
and reason. Withdrawal uses `withdraw`, a nonzero reviewer-stream predecessor
and the exact candidate coordinates, but must omit `--bundle`.

For a reviewed merge, create a separate input and request directory under the
merge submitter's credential. Use `action:"merge"`; retain the exact shared
candidate coordinates, remove `expected_version` and `reason`, and supply:

```json
{
  "required_reviewers": ["44444444444444444444444444444444"],
  "method": "merge-commit"
}
```

These are fields in the merge input, not a whole input. Its `scope.principal_id`
must identify the authenticated submitter and cannot be in the reviewer set.
Supply the candidate bundle during `prepare`. The merge `send` requires both
`--confirm-candidate EXACT_CANDIDATE_OID` and
`--confirm-merge-method merge-commit`. Select `squash` in both the prepared
method and the confirmation for a squash candidate obtained from native tooling.
Neither flag changes a saved candidate or proves that required reviews exist.
The native driver owns strategy validation and the current review/protection gates.
A merge-commit candidate cannot be silently converted to squash by this client.

### Saved bytes and interruption

Preparation copies and verifies the bounded bundle before asynchronous I/O. It
creates a new private request directory, writes/syncs `candidate.bundle` (at most
16 MiB), syncs the directory, then writes/syncs `intent.json` and its directory
and parent. The small intent selects the exact bundle length and SHA-256 checksum.
It embeds neither bundle bytes nor an operator-supplied file path. The original
input bundle is no longer needed after successful preparation. Original six-action
slots and withdrawal slots still contain only `intent.json`.

A new send revalidates/resyncs the intent and fixed-name saved bundle before
network admission. Changed, truncated, missing, oversized, public, linked or
special bundle files refuse; no substituted filename, new key or candidate is
selected. Private reads use bounded allocation and exact device/inode/size and
nanosecond modification/change observations. These checks rely on owner-controlled
parents, not protection from a hostile concurrent parent-directory replacement.
Filesystem work is bounded in bytes but lies outside the network deadline; OS
filesystem calls are not a hard real-time cancellation guarantee.

An interrupted slot is never removed, completed or overwritten automatically.
A bundle-only slot or incomplete intent is not a prepared request. Retain it
for diagnosis. A complete original intent is sufficient for **outcome recovery**
even when bundle bytes have subsequently been lost or damaged:

```sh
node scripts/remote_pull.mjs recover --request-dir /private/approval-37 \
  --token-file /private/original-or-rotated-token \
  --record /private/approval-recovered.json \
  --known /private/approval-result.json
```

Omit `--known` when no complete prior record exists. Recovery never opens the
bundle and accepts neither bundle nor candidate/method confirmation flags.
A retained terminal outcome or publication supplied using `--known` also allows
`send` to skip the bundle and perform only the original-key lookup. Without that
retained evidence, a send with no usable bundle refuses locally: use `recover`
rather than guessing whether a previous attempt committed. An absent outcome
does not prove that nothing was published.

Result-file publication and exit codes remain the existing ones: new immutable
records only; 0 for confirmed commit, 1 for native refusal, 2 for pre-network
local failure, 3 for incomplete/unknown work or output failure. Valid terminal
evidence remains in a record or diagnostic when result publication races or
stdout is lost. SIGTERM/SIGINT close the owned network operation; SIGKILL leaves
the original synced request for explicit recovery. These are process/filesystem
tests, not a universal hardware power-loss guarantee.
