# The canonical-codec golden corpus

63 files: 9 valid vectors and 54 planted defects, six per identity-bearing
schema. Each file carries the canonical bytes as hex, the expected body id, and
for a defect the refusal it must produce.

## The property that makes this corpus worth having

**The bytes were derived independently from the written format specification.
They were not emitted by the encoder under test.** That is the entire value: a
corpus generated by the implementation it checks proves only that the
implementation is self-consistent, and would happily bless a wrong format
forever. Every header in these files says so, and it must stay true.

The generator is deliberately *not* in this repository. It is a separate
implementation in another language, kept outside the tree so that no future
refactor can quietly couple it to `fgit-codec` and destroy the independence.
Its absence is the point; do not add a Rust regeneration helper here.

## Reserved code points

Fixtures use `0xfff1` for both the digest algorithm
(`harness::CORPUS_ALGORITHM_CODE_POINT`) and the signature scheme
(`harness::FIXTURE_SIGNATURE_SCHEME_CODE_POINT`). `fgit-crypto` reserves
`0xfff0..=0xffff` in both namespaces so that "this number is never real" means
one thing everywhere.

**Never give a fixture a production code point.** The corpus previously carried
signature scheme 1 with a 64-byte payload; ADR-0003 Amendment 1 then allocated
code point 1 to Ed25519, whose signatures are exactly 64 bytes, and those
fixtures became *shaped* like real signatures — right scheme, right length,
separable only by an actual verification. Moving them cost a 14-file re-bless
(commit `740a253`). Choosing a reserved point up front costs nothing.

Note that `fgit-crypto::resolve_signature_scheme` *refuses* the reserved range
as `ReservedForHarness`. Nothing in `fgit-codec` resolves a code point —
`SignatureSchemeId` accepts any non-zero value — so the reserved points are
inert here. A consumer that does resolve must not be handed these fixtures.

## Re-blessing procedure

Regenerating goldens is a normal engineering act with one abnormal failure
mode: it can be used to make a failing test pass, which is forbidden (RH-3 in
`AGENTS.md` §16.3). The procedure exists to make the difference legible in the
diff rather than resting on the committer's word.

1. **State the cause first.** A re-bless is justified by a change to the format,
   the identity rule, or a code-point allocation — never by "the test is red".
   If a test is red and the format did not change, the code is wrong, not the
   corpus.

2. **Run the control before the treatment.** Regenerate with the change *not*
   applied and confirm the output reproduces the currently committed corpus
   **byte-identically**. Without this, a diff cannot be attributed to your
   change rather than to drift that accumulated since the last re-bless. If the
   control does not reproduce the corpus, stop: something already diverged and
   that is the real finding.

3. **Characterise the diff before landing it.** Record how many files move and
   why every one of them had to. Check specifically that:
   - frame lengths are unchanged unless the change is *about* length, since a
     length shift cascades through every length prefix that follows it;
   - **canonical ordering is preserved.** Collections sort by encoded bytes, so
     a change to an early field can silently reorder a set. An ordering test
     keeps passing while asserting a different arrangement — it does not fail,
     it quietly stops testing what it named.

4. **Preserve the negatives.** Every planted defect must keep its expected
   refusal, and the test count must not drop. A re-bless that reduces coverage
   is a coverage change wearing a regeneration's clothes.

5. **Commit it visibly.** Cite the control result, the treatment bounds, and
   this procedure in the commit message, and say plainly why the change is not
   RH-3. `740a253` is the worked example.

## Reading a golden

```
schema = signed-envelope     # which schema family
kind   = valid | <defect>    # defect name matches the filename suffix
frame_len, canonical_body_len
body_id = <domain>/<codec version>/alg:<code point>/<digest>
bytes  = <hex of the full frame>
```

`canonical_body_len` covers the payload only. Per
NORMATIVE_PROTOCOL_CONTRACTS §3.2 the transport frame is **excluded** from the
digested bytes, so the body id is computed over the payload and not over the
frame. This crate got that wrong once and fixed it at `158c899`; the goldens
are what keep it fixed.
